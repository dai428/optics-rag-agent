## 三、核心概念：LangGraph 到底在干什么

### 3.1 一句话理解

**LangGraph = 一张流程图 + 一块共享白板。**

- **节点（Node）**：图上的工位，一个工位干一件事。
- **边（Edge）**：工位之间的传送带。
- **状态（State）**：「共享白板」，所有工位都能看、都能往上写。

打个比方：以前你写代码是**一条直线**——第 1 行、第 2 行、第 3 行，从上往下走。

LangGraph 是**画在墙上的流程图**——哪个工位干完活该传给谁，用箭头画出来；条件分支就是「如果 A 就走左边，否则走右边」。

好处？**流程能被看见、能被改、能被讲。**

### 3.2 你的流程图长这样

```
              ┌──────────────┐
   __start__ →│   rewrite    │  改写问句
              └──────┬───────┘
                     │
          ┌──────────┴──────────┐
          │  route_after_rewrite│   ← 条件边：是闲聊吗？
          └──────────┬──────────┘
                     │
         ┌───────────┴────────────┐
         │                        │
    不是闲聊                   是闲聊
         ↓                        │
   ┌──────────┐                   │
   │ retrieve │  检索             │
   └────┬─────┘                   │
        └──────────┬──────────────┘
                   ↓
             ┌──────────┐
             │ respond  │  生成回答
             └────┬─────┘
                  ↓
               __end__
```

**三个节点，四行代码就能讲完：**

1. **rewrite** —— 用户说「那它的定标怎么做」，先把「它」换成「LCVR」，变成完整问句。
2. **retrieve** —— 拿完整问句去向量库取最像的 3 个片段。
3. **respond** —— 把 3 个片段 + 用户问题一起喂给大模型，让它照着资料答。

**一条条件边**：`route_after_rewrite` 判断「这句是闲聊吗」。是闲聊就不检索，省一次向量查询。

## 四、四个文件，逐个讲清

### 4.1 `state.py` —— 定义白板上记什么

```python
@dataclass(kw_only=True)
class State(InputState):
    queries: Annotated[list[str], add_queries] = field(default_factory=list)
    retrieved_docs: list[Document] = field(default_factory=list)
```

**这里有一个必须会讲的语法点：`Annotated[..., add_queries]`**

`Annotated` = 注解（annotation），字面意思是「给这个类型附加一条额外说明」。

`add_queries` 是一个**归约函数（reducer）**，长这样：

```python
def add_queries(existing, new):
    return list(existing) + list(new)
```

**它解决什么问题？**

LangGraph 里，节点返回 `{"queries": ["新问句"]}` 时，默认行为是**覆盖**——原来的列表被整个换掉。

加上 `Annotated[list[str], add_queries]` 之后，行为变成**追加**——新旧拼在一起。

> 类比：`add_queries` 就是「往杯子里续水」，而不是「把杯子倒空再装」。
> LangGraph 里最常用的那个 `add_messages` 是同一个套路，只不过它是给消息列表用的。

**为什么用 `dataclass` 不用 `dict`？**

| | dict | dataclass |
|---|---|---|
| 取字段 | `state["messages"]` 要打引号 | `state.messages` 有自动补全 |
| 写错名字 | 运行时才炸 | 编辑器当场报红 |
| 类型提示 | 只能靠注释 | 声明式，可被检查 |

`kw_only=True` 的意思是「**只能用关键字传参**」。也就是必须写 `State(messages=[...])`，不能写 `State([...])`。好处是参数一多不容易传错位置。

### 4.2 `configuration.py` —— 每次调用换参数

**问题**：图编译一次很慢（实测 36 秒，要加载嵌入模型）。如果每次改个「检索几条」就重新编译一次，服务没法用。

**解法**：编译一次，调用时传参数进去。

```python
config={"configurable": {"thread_id": "abc", "retrieval_k": 5}}
```

节点里用 `Configuration.from_runnable_config(config)` 取出来。

**`from_runnable_config` 做了什么？**

```python
valid = {f.name for f in fields(cls)}   # 拿到本类声明的所有字段名
kwargs = {k: v for k, v in configurable.items() if k in valid and v is not None}
```

翻译成人话：
1. 先看自己有哪些字段（`retrieval_k`、`response_system_prompt`、`query_system_prompt`）
2. 从 config 里**只挑自己的字段**，别人的（比如 `thread_id`）忽略
3. 值为 `None` 的也忽略 —— 表示「用默认值」
4. 剩下的拼成参数，构造对象

**这是个很典型的「白名单过滤」模式**，在很多地方都能用：只接受自己认识的键，多出来的全部丢掉。这样 LangGraph 往 config 里塞什么新东西，都不会把你的代码搞崩。

### 4.3 `rag_graph.py` —— 核心，手写流程

**节点函数的统一签名：**

```python
def 某节点(state: State, config: RunnableConfig) -> dict:
    ...
    return {"要更新的字段": 新值}
```

**两个必须记住的规矩：**

1. 第一个参数是 state（读白板），第二个是 config（读本次调用的参数）
2. **返回值是 dict，只放要改的字段** —— 不是返回整个 state。框架会自动合并。

> 这就是为什么需要归约函数：框架拿到你的 `dict`，按字段名找到白板上对应的位置，然后用归约函数决定是覆盖还是追加。

**`rewrite_query` 节点的完整逻辑：**

```python
history = _history_text(state.messages[:-1])
if history == "（无历史对话）":
    return {"queries": [question]}     # 首轮：原话直接用

# 多轮：让模型把省略句补全
rewritten = llm.invoke(prompt).content.strip()
if not rewritten or len(rewritten) > 200:
    rewritten = question              # 兜底
return {"queries": [rewritten]}
```

三个设计取舍，都是面试能用的话术：

**取舍 1：为什么首轮不调模型？**

因为没有历史可参考。改写的前提是「有上下文可供补全」，首轮没有。直接原话用，**省一次 2~5 秒的模型调用**。

**取舍 2：为什么要兜底？**

大模型不可靠 —— 它可能返回空串、可能啰嗦几百字、可能把问题也答了。所以必须防：

- `not rewritten` → 空串
- `len(rewritten) > 200` → 太长了，肯定不是问句

任何一条触发，就退回用原话。**宁可改写失败，也不能让整条流程挂掉。**

**取舍 3：为什么异常也退回原话？**

```python
try:
    rewritten = llm.invoke(prompt).content.strip()
except Exception:
    rewritten = question
```

因为改写只是**锦上添花**，不是主流程。它挂了不该连累整个问答。这是「**降级（fallback）**」思想 —— 好学生也能说清楚。

**`route_after_rewrite` 条件边：**

```python
def route_after_rewrite(state: State) -> str:
    question = state.messages[-1].content
    return "respond" if _is_chitchat(question) else "retrieve"
```

**这里有个关键设计取舍，一定要会讲：**

我本来可以让**模型**来判断「这句要不要检索」。但最后用了 **10 行规则**：

```python
_CHITCHAT = ("你好", "您好", "hi", "hello", "在吗", "谢谢", ...)

def _is_chitchat(text):
    t = text.strip().lower()
    if len(t) <= 4:              # 极短句
        return True
    return any(kw in t for kw in _CHITCHAT) and len(t) <= 12
```

**为什么用规则不用模型？** 两个理由：

1. **省钱省时间**：一次模型调用 2~5 秒。规则判断是**微秒级**。每天的对话里闲聊占比不低，这一省很可观。
2. **确定性**：规则永远给同样的答案。模型可能「今天心情不好就不检索了」—— 这种**抖动（非确定性）**在工程上是灾难，因为你没法复现 bug。

> 面试话术：「这类『要不要走某条路』的判断，只要能用规则稳定判准，就不该交给模型。模型该用在真正需要理解语义的地方。」

**组装图：**

```python
builder = StateGraph(State, input_schema=State)
builder.add_node("rewrite", rewrite_query)
builder.add_node("retrieve", retrieve)
builder.add_node("respond", respond)

builder.add_edge(START, "rewrite")
builder.add_conditional_edges(
    "rewrite",
    route_after_rewrite,
    {"retrieve": "retrieve", "respond": "respond"},   # 返回值 → 目标节点 的映射表
)
builder.add_edge("retrieve", "respond")
builder.add_edge("respond", END)

graph = builder.compile(checkpointer=checkpointer)
```

`add_conditional_edges` 三个参数：
1. 从哪个节点出发
2. 用哪个函数做判断
3. **映射表**：判断函数的返回值 → 实际跳转到哪个节点

那个映射表很重要 —— 它让你**节点名字和判断逻辑解耦**。判断函数只管返回 `"retrieve"` 这种语义化的词，映射表决定它对应哪个节点。

**`checkpointer` 是会话记忆的原理：**

```python
graph = build_graph_with_memory()   # 内部：InMemorySaver()
```

传了 `checkpointer` 之后，每次调用传同一个 `thread_id`，框架就自动把历史 messages 一起带上。这就是「**它记得上一轮聊了什么**」的全套实现。

> `InMemorySaver` 的「InMemory」意思是**存内存**——进程一重启就没了。生产环境要换成 Redis 或数据库版本的 checkpointer。这也是面试可能追问的点。

### 4.4 `config.py` 的超时设计（实测踩出来的坑）

**这是本次唯一一个「真踩到、真修了」的工程问题**，面试讲这个非常有说服力。

**现象**：用 HTTP 服务测多轮对话，第二轮报 `模型响应超时，请稍后重试`。

**排查**：

1. 先看是不是代码 bug —— 用 CLI 跑同样三轮，**成功**。说明代码没问题。
2. 那就是超时配置问题。查 `.env`：模型是 `Qwen3.8-27B`，**这是推理模型**（会先生成思维链再给答案）。
3. 实测单次调用耗时：CLI 那轮总耗时 5 分 19 秒，跑 3 次模型调用 —— **平均每次 100 秒以上，最长的接近 6 分钟**。
4. 而原来的 `request_timeout` 写死 **120 秒**。第二轮要串行调两次模型（改写 + 回答），必然超时。

**修法 —— 为什么不是简单地把 120 改成 600？**

因为**改写成和回答是两个不同性质的任务**：

| | 查询改写 | 正式回答 |
|---|---|---|
| 任务 | 只输出一句问句 | 要组织完整答案 |
| 输出长度 | 十几字 | 几百字 |
| 需不需要思维链 | 不需要 | 需要 |
| 合理超时 | 60 秒 | 600 秒 |

如果统一改成 600 秒，改写卡住时要等 10 分钟才报错 —— 用户早就关了页面。

**所以拆开：**

```python
rewrite_timeout: int = 60     # 查询改写：任务简单
request_timeout: int = 600    # 正式回答：可能触发长思维链
rewrite_model: str = ""       # 可选：给改写专门换个小模型
```

配合 `build_llm(purpose)` 分流：

```python
def build_llm(purpose: str = "answer"):
    if purpose == "rewrite":
        model = settings.rewrite_model or settings.llm_model
        timeout = settings.rewrite_timeout
    else:
        model = settings.llm_model
        timeout = settings.request_timeout
    ...
```

**这个设计的面试价值**（一定要会说）：

> 「我一开始超时是写死的 120 秒。实测发现用的是 27B 推理模型，单次最长要 6 分钟，直接超时了。
>
> 但我没有简单地把超时调大 —— 因为改写和回答是两个不同量级的任务。改写只要输出一句问句，卡住就该快速失败；回答要长思维链，必须给足时间。所以我按用途拆成两档，还预留了给改写单独指定小模型的口子。
>
> 这里的原则是：**超时不是「越大越好」，而是「按任务的正常耗时设定」，让异常尽早暴露。**」

**附：偶发超时的定位过程（这段更有价值）**

修完超时后，测试中仍偶发超时。我做了三步定位：

1. **先看服务端日志** —— 统计状态码分布：`200 OK` 出现 4 次、`504` 只出现 1 次。说明**不是稳定失败**。
2. **做对照实验** —— 绕开 RAG 图，直接调模型，只花 **11 秒**返回。说明**模型端本身不慢**。
3. **对比同一请求的不同时刻** —— 同一个「那它的定标怎么做」：一次 1 分 45 秒成功，另一次超时。

**结论**：`AMD 共享模型有 16 并发上限`。高峰期排队时，长调用（生成几百字带引用的答案）会被拖到超时；空闲时几十秒就回来。

**这段经历在面试里怎么讲**：

> 「改完之后还是有偶发超时，我没有当成 bug 去改代码，而是先量化 —— 打日志统计状态码分布，发现 200 和 504 的比例是 4:1，说明是间歇性的。然后又做了个对照实验，绕开整个链路直接调模型，11 秒就返回了，排除了模型本身的性能问题。最后定位到是**共享模型的并发排队**，属于外部依赖的容量限制，不是我的代码问题。
>
> 这让我意识到一件事：**排查问题要先区分「我的代码」和「外部依赖」，不要一超时就怀疑自己。** 用最小复现把变量隔离出来，比通读代码快得多。」

> 这个案例的含金量在于：展示了**先量化、再隔离变量、最后定位**的排查方法论，而不是「试了半天终于好了」。

### 4.5 `knowledge_base.py` 修的那个坑

**问题**：`glob("**/*.md")` 到底匹配什么？

很多人以为 `**` 是「任意路径」，包括当前目录。**错。**

`pathlib` 里的 `**` 意思是「**至少一层**子目录」。所以：

- ✅ 匹配：`实验报告/xxx.md`
- ❌ **不匹配**：`docs/根目录下的文件.md`

**后果**：你哪天往 `data/docs/` 根目录扔一个文件，它会被**静默忽略** —— 不报错，就是查不到。这种 bug 最难查，因为没有报错信息。

**修法**：补上顶层模式。

```python
_PATTERNS = ("*.md", "*.txt", "*.csv",           # 顶层
             "**/*.md", "**/*.txt", "**/*.csv")  # 子目录
```

**但这样又产生新问题**：`实验报告/xxx.md` 会被 `**/*.md` 匹配到，会不会被 `*.md` 也匹配到？

不会 —— `*.md` 不跨目录。**但 `**/*.md` 和更深的 `**/**/*.md` 会重叠**。所以必须去重：

```python
seen: set[str] = set()
for pattern in _PATTERNS:
    for f in sorted(settings.docs_dir.glob(pattern)):
        if str(f) in seen:
            continue        # 已处理过，跳过
        seen.add(str(f))
        docs.extend(TextLoader(str(f), encoding="utf-8").load())
```

**`set` 去重是 O(1) 查找**，比 list 的 O(n) 快。文件多了差距明显。

**验证**：改完重跑，文件数 14、片段数 869 —— **和改之前完全一致**，说明去重生效，没有重复建库。

## 五、面试怎么讲这个项目（5 分钟版）
### 开场（30 秒）

> 「我做了一个面向光学实验数据的 RAG Agent。语料是我自己硕士课题的 14 篇真实材料 —— LCVR 液晶偏振计的实验报告和论文，切出 869 个片段。整个链路我自己跑通了，检索层的 Recall@10 是 85%，关键词覆盖 100%。」

**为什么这么开场？** 三个信息一次给到：**真实语料**（不是玩具数据）、**有量化指标**（不是「跑通了」）、**和专业背景强绑定**（不是烂大街的客服问答）。

### 主体（3 分钟）

**第一层：这是什么**

> 「用户问光学专业问题，系统先从我的知识库里检索相关材料，再让大模型**基于这些材料**回答，并标注来源。核心解决的是大模型**幻觉**——它不懂 LCVR 的具体参数，但会一本正经编。」

**第二层：怎么做的（讲流程图）**

> 「我用 LangGraph 编了一张三节点的图：**改写 → 检索 → 回答**。
>
> 改写节点是关键 —— 用户多轮对话时会说『那它的定标怎么做』，这个『它』直接拿去检索是查不到东西的。所以先让模型把『它』补成『LCVR』，变成完整问句。
>
> 中间有一条条件边：如果这句是闲聊，就走另一条路直接回答，不检索。
>
> 检索节点用本地的 BGE 中文嵌入模型，Chroma 做向量库。回答节点把检索到的 3 个片段拼进提示词，要求模型严格基于资料作答。」

**第三层：为什么这么设计（讲取舍）**

这是**面试官最想听的部分**，准备三个：

> **取舍一：闲聊判断用规则不用模型。** 因为模型调用要 2~5 秒且结果不确定，规则是微秒级且永远一致。能用规则稳定判准的，不该交给模型。
>
> **取舍二：改写失败静默降级。** 改写只是锦上添花，它挂了就退回用原话，不能让整个问答失败。
>
> **取舍三：嵌入模型用本地的，生成模型用云端的。** 嵌入要跑 869 个片段、每次提问还要跑一次，用 API 又慢又贵；而且本地模型离线可用。生成模型只在最后一步调用一次，用云端的大模型效果好。

> **取舍四：超时按任务量级分档。** 改写 60 秒、回答 600 秒。因为 27B 推理模型单次最长要 6 分钟，写死 120 秒必超时；但统一放宽又会让小任务卡死太久。原则是「按正常耗时设定，让异常尽早暴露」。

### 收尾（30 秒）

> 「我还做了检索层评测，20 道题，Recall@10 是 85%。分析下来瓶颈不在『找不到』，而在『排序深度』—— 有 3 道题正确答案排在 7 到 16 位。所以下一步计划做**混合检索 + Rerank**。」

**这一段的价值**：主动暴露问题 + 给出改进方向，展示的是**工程判断力**，不是「我做完了」。

## 六、可能的追问 & 标准答法

**Q1：为什么不用 `create_agent` 一行搞定？**

> 「我两个都实现了。`create_agent` 是黑盒——内部是 ReAct 循环，模型自己决定调不调工具。它能跑，但我想加查询改写和闲聊路由，黑盒改不了。所以我用 LangGraph 自己把流程画出来，每一步都可控可观测。留着黑盒版是做对照。」

**Q2：`Annotated[..., add_messages]` 是什么？**

> 「这是 LangGraph 的**归约函数**机制。默认节点返回同名字段是**覆盖**，加了归约函数变成**追加**。`add_messages` 是官方给的，专门处理消息列表——它还会按消息 id 去重更新。我自己也写了一个 `add_queries` 处理问句列表，逻辑就是 `existing + new`。」

**Q3：会话记忆怎么实现的？**

> 「编译图时传了 `checkpointer=InMemorySaver()`。调用时传同一个 `thread_id`，框架就自动把历史消息带上。原理是 checkpointer 在每个节点执行后把状态存一份快照。注意 `InMemorySaver` 存在内存里，进程重启就丢，生产环境要换成持久化的。」

**Q4：怎么防止模型胡说？**

> 「三道防线。第一，提示词里明确要求『严格基于检索资料，资料没有的就说没找到』。第二，检索结果带来源文件名，要求回答标注出处。第三，我在提示词里还加了一条——『如果资料只覆盖问题的一部分，就只答覆盖的部分，并说明哪些部分未涉及』。实测效果不错，第三轮那个问题的回答末尾，模型主动列出了三项『资料未涉及的部分』。」

**Q5：为什么切块大小是 300？**

> 「先说明这是**经验值**，不是算出来的。中文 300 字大约是一个完整论述段落的长度 —— 太小会切断语义，太大检索精度下降（一段里混了多个主题）。重叠 50 是为了防止关键句正好被切在边界上。这块我还没做实验对比，属于下一步的调优项。」

> ⚠️ **注意**：这题**千万不要硬编数字**。老实说「经验值，还没做对比实验」比编一个听起来很专业的数字安全得多。面试官一眼能看出编的。
