一、项目定位与动机

开场题。答不清"为什么做"，后面全白搭。
Q1用一句话讲清你这个项目干了什么。必背
我基于 LangChain 的 Agent 框架 + FastAPI + Chroma 向量库，构建了一个光学领域的 RAG 智能问答服务：把偏振测量资料建成本地知识库，模型回答前会自己判断要不要检索，检索到相关内容后基于它作答，并支持多轮会话记忆与 HTTP 接口调用。
一句话里必须同时有：做了什么（RAG 问答）＋怎么做的（Agent/向量库/服务化）＋面向谁（光学领域）。
Q2这个项目跟你的光学背景什么关系？必背
不是硬编出来的：我读研做的是 LCVR（液晶可变相位延迟器）偏振测量，日常要查大量偏振仪、Stokes 参量、Mueller 矩阵、定标资料。我就把自己真正会用的资料做成知识库，让 Agent 帮我问答。领域知识 + Agent 工程能力的组合，是市面上稀缺的。
面试官最怕"通用 demo 套壳"。你的护城河是：别人抄得走 RAG 代码，抄不走你对光学数据的理解。
Q3为什么从光学转向 AI Agent 方向？
不是放弃光学，是做交叉。AI Agent／大模型应用岗的 JD（职位描述）普遍只要求"本科及以上"，真正卡人的是有没有可跑通、可讲透的项目。我把光学领域的真实需求做成 Agent 项目——这就是"垂直领域 + Agent"的错位竞争。
把"转行"讲成"叠加"，而不是"抛弃"。

二、RAG 原理（必背区）

这层答不出来，初面就止步了。
Q4什么是 RAG？解决什么问题？必背
RAG = 检索增强生成。让大模型回答前先"查资料"，把检索到的相关片段塞进提示词（Prompt）再让它照着答。解决三件事：①幻觉（模型编造）②知识时效（训练截止后的事不知道）③私域知识（个人/企业资料它没见过）。
模型参数是"冻结"的，只会回忆不会查证；RAG 等于给它接了块"外挂硬盘"。
Q5既然要注入知识，为什么不直接微调（Fine-tuning）？必背
RAG 改的是"它知道什么"，微调改的是"它怎么说话"。
要注入事实知识 → 用 RAG：不动权重、资料随时更新、便宜、可溯源到原文。
要改风格/格式/领域语气 → 用微调：要重训、贵、知识更新还得重训。
我的场景是"问答知识库"，不是"让它学会某种语气"，所以 RAG 是最优解，二者还可结合。
Q6RAG 的完整流程？必背
两阶段。
· 离线建库：加载文档 → 切块（chunk）→ 向量化（embedding）→ 存入向量库
· 在线问答：问题向量化 → 检索 Top-K 相似片段 → 拼进 Prompt → LLM 生成
建库是"一次性重活"，问答是"每次都要跑的轻活"。我项目里分别对应 knowledge_base.py 与 rag_agent.py。
Q7什么是 Embedding（嵌入）？必背
把文本映射成高维向量（我用的是 512 维）的模型；语义相近的文本，向量距离就近。我项目用的是本地开源的 BAAI/bge-small-zh-v1.5。
"离得近＝意思像"不是数学必然，是训练出来的——模型在海量语料上学到"常一起出现的表达该靠近"。换个模型，同一句话的坐标就变了。
Q8为什么用向量检索，不用关键词检索？必背
关键词检索（BM25）只匹配字面——搜"液晶可变延迟器"命不中只写了"LCVR"的段落；向量检索懂语义，但对专有名词、精确短语容易漏。所以生产环境常用混合检索（两者加权/融合）。
一个懂"意思"、一个懂"精确词"，互补。
Q9为什么要切块（chunk）？
① 检索要有粒度：不切，向量库最小单位就是"整篇"，搜什么命中的都是整篇，等于没筛；② 嵌入模型有输入长度上限（BGE 只吃 512 token），超长会被截断；③ 塞进 Prompt 的 token 也有限。
切块的本质是"把检索的抓手变细"，不是为了塞给模型方便。
Q10余弦相似度 vs 欧氏距离？为什么常用余弦？
余弦算两向量夹角（只看方向），欧氏算直线距离（方向+长度都看）。文本向量关心"语义方向"而非"文本长短"，所以余弦更常用。
一篇长文和一句短语，只要意思一样方向就该一致；长度差异不该影响判断。向量归一化后两者等价。

三、检索与参数（陷阱区）报告数字者死

这层是面试官最爱挖的地方——光报"300、k=3"没用，他会问"凭什么是这个数"。
Q11chunk 切多大？为什么是 300？陷阱
我用 chunk_size=300 字符。依据：① 我的知识库是条目式技术资料（一段一个知识点，塞 300 字够装一整个概念）；② 中文技术文本在 300 字左右通常只有一个主题，过大 → 语义被稀释、检索命中整块但只有一句有用；过小 → 上下文断裂，答案拼不全。
chunk_size 没有万能值，它是"信息密度"与"语义完整性"的权衡，要拿自己语料试。正确答法是"我按资料特性选了 300，并能说清偏大偏小各自坏在哪"。
Q12chunk_overlap 为什么设 50？陷阱
重叠 50 字，是为了避免关键信息正好被切在边界上——上一块结尾和下一块开头有 50 字重叠，保证跨界的句子在两块里都完整出现。
重叠是"用一点存储冗余，换检索不漏"的保险。太小会切裂语义，太大则库冗余、匹配重复。
Q13top-K 取几条？为什么是 3？陷阱
我取 k=3。依据：知识库小（6 个片段），取 3 条已能覆盖最相关的上下文；k 太大会把不相关的片段也塞进 Prompt，稀释注意力、增加 token 成本、反而降质；k 太小则可能漏掉答案所在片段。
k 是"召回率"与"信噪比"的平衡。真正的做法是看评测指标（Recall@k / NDCG）来定 k，而不是拍脑袋——这也是我要补的升级点。
Q14嵌入模型为什么选 bge-small-zh-v1.5？
三个理由：① 中文优化（智源 BGE 的中文效果在同体量里靠前）；② small 版只有约 100MB、512 维，CPU 就能跑，本地免费、无需 API Key；③ 我这是教学/自用规模，不需要上千维的大模型。
选型要看"效果 × 成本 × 部署"三角。生产上如果数据量大、精度要求高，会换成大模型或用云端 embedding。
Q15检索效果不好，你怎么排查？进阶
按链路逐段定位：① 先看切块——命中片段是不是答所在块（不是 → 调 chunk/overlap）；② 看嵌入——同义不同词能否互相召回（不能 → 换模型）；③ 看 k 与相似度阈值——是不是排到 k 外了；④ 看 query 表述——用户口语化问题要不要做改写（query rewrite）。
RAG 的瓶颈多半在检索，不在生成。面试官爱听"先怀疑检索质量"，而不是"怪模型不行"。

四、架构与选型

考你"会不会做工程决策"，不只是"会不会调库"。
Q16为什么要把 Agent 做成 FastAPI 服务，而不是一个脚本？
脚本是"跑一次就退"，无法被其他程序调用、无法并发、没有会话。做成 FastAPI 服务后：① 对外暴露标准 HTTP 接口（/chat），前端/其他系统都能调；② 支持多轮会话（按 session_id 隔离）；③ 自动生成交互式接口文档（/docs）；④ 是"工程"而不是"玩具"。
面试官靠"有没有服务化"判断你是"会调库"还是"懂工程"。这正是一梯队到二梯队的分水岭。
Q17为什么用 Chroma？不用 FAISS？
Chroma 的优势是轻量 + 自带持久化 + 与 LangChain 原生集成：几行代码就能建库、落盘后重启不丢。FAISS 更像纯向量索引库，持久化和元数据管理要自己搞，适合大规模性能场景。我这个规模，Chroma 是性价比最优。
选型讲"匹配场景"。小项目上 Milvus 是过度设计，大项目用 Chroma 又不够，关键是能说清边界。
Q18你把旧版的 InMemoryVectorStore 换成了 Chroma，为什么？
旧的 InMemoryVectorStore 是纯内存的——进程一重启，向量库就没了，每次都要重建，根本不能做服务。换成 Chroma 持久化后，建库一次、落盘复用，服务重启秒级可用。
这是"能不能做成服务"的前提。持久化是工程化的第一步。
Q19为什么不用老的 RAG 链（LCEL），要用 Agent？进阶
老链是无条件检索：你问"你好"，它也会去查一遍库、浪费 token，还常把不相关内容塞进上下文。Agent 把检索变成"工具"，由 LLM 自己决定要不要调——闲聊直接答，专业问题才检索。这更接近真实用户行为。
这就是 Agentic RAG（智能体式 RAG） 与传统 RAG 的本质区别：把"固定流水线"换成"模型自主决策"。

五、Agent 机制（重点区）

JD 里出现频率最高、最能拉开差距的一层。
Q20create_agent 是什么？和"链（Chain）"什么区别？必背
create_agent 是 LangChain v1 的新版 Agent 构造器（取代老教程里的 create_retrieval_chain）。链是写死的流水线（一定按 A→B→C 走）；Agent 是给模型一组工具 + 一个循环，由模型自主决定调用哪个工具、调几次、什么时候结束。
链＝"我规定路径"；Agent＝"模型自己选路径"。这就是"会调库"和"会搭 Agent"的分界线。
Q21LLM 是怎么"决定要不要调工具"的？必背
靠 tool calling（工具调用）：我把检索包成一个带名称和描述的工具传进模型，模型在生成时如果判断需要外部信息，就不直接输出答案，而是输出一个"调用某工具、参数是某查询"的结构化请求；框架执行工具拿到结果，再回喂给模型，模型据此生成最终答案。这是个可循环的过程（ReAct 范式）。
关键点：决定权在模型，不在代码。工具的描述（description）写得好不好，直接影响模型判断得准不准。
Q22检索是怎么变成"工具"的？
用 create_retriever_tool(retriever, name, description) 把检索器包装成工具。我写的描述是"回答偏振仪、LCVR、Stokes 参量、Mueller 矩阵、定标等问题前，必须先调用本工具"——这段描述就是给模型看的"使用说明书"。
工具描述越明确触发条件，模型越不会"该查不查"或"乱查"。
Q23你怎么知道这一问到底有没有触发检索？
我在返回里加了 used_retrieval 字段：判断本轮消息序列里有没有出现 ToolMessage（工具消息）——有就说明模型调过检索工具。实测闲聊"你好"→false，专业问题→true。
这是"Agent 自决检索"的可观测证据——能证明给面试官看，不是嘴上说。
Q24如果模型不支持 tool calling 怎么办？进阶
两条路：① 退化为"固定检索链"——无条件先检索再生成（牺牲效率保功能）；② 提示词工程——让模型输出约定格式（如"需要检索：关键词"），代码解析后去检索再二次调用。但最省的还是换一个支持工具调用的模型。
面试官想看你知道"Agent 依赖 tool calling 这个前提"。不是所有模型都能当 Agent 的大脑。
Q25Agent 判断"不用检索"时，会不会该查不查、导致答错？陷阱
会，这是 Agentic RAG 的固有风险——模型判断错就会漏检、进而幻觉。我的缓解手段：① system_prompt 里明确列出必须检索的问题类型；② 工具描述写清触发条件；③ 答案约束"只能基于检索内容，没有就说未找到"。要更稳的话，可以加"答案自检"或强制检索兜底。
诚实承认风险 + 给出缓解方案，比硬说"不会错"加分得多。面试官就是在试你有没有想过边界。

六、工程细节

考"真实上线会踩的坑"，这层最能体现你不是只会跑 demo。
Q26多轮会话记忆怎么做的？会话隔离呢？必背
用 InMemorySaver 作为 checkpointer（检查点存储器）。每次调用传入 config={"configurable":{"thread_id": session_id}}，框架按 thread_id 隔离每个会话的历史消息——同一个 session_id 记得上下文，换一个就是全新会话、互不串号。
thread_id 就是"会话的身份证"。我把 session_id 校验限制为字母数字和 ._:-，防注入。
Q27InMemorySaver 是内存的，服务重启记忆就没了，生产怎么办？进阶
对，内存版只适合开发/单机。生产要换成持久化 checkpointer：把会话状态存进数据库（如 PostgreSQL / Redis），LangGraph 支持接 PostgresSaver 这类存储后端；多实例部署时还要保证同一会话路由到能读到同一份状态。
这题是"你知道当前方案的短板、也知道怎么补"的经典考法。答"不知道"就暴露了没想过生产。
Q28并发上来了、模型报 429 限流，你怎么处理？
我实测过：AMD 的共享模型有并发上限 16，打满就返回 429 Too Many Requests。我的处理：① 客户端超时放宽到 120s + 自动退避重试；② 服务端捕获 429 并返回友好的 429 提示，而不是崩成 500。
生产上还要加队列/令牌桶限流、多模型路由（打满切备用模型）。能说出"限流是共享资源的必然"就到位了。
Q29你服务启动慢，怎么优化的？进阶
根因是重型依赖（torch，约 10.5s）被顶层导入，把冷启动拖到 12s。我把这些 import 从模块顶层下沉到函数内部（惰性加载）——端口 0.6s 就可用，首次请求才付加载代价。实测冷启动 12.4s → 0.61s。
这题证明你会看"启动耗时构成"，而不是盲加机器。惰性导入是服务化项目的通用优化。
Q30你代码里为什么要在主线程预导入 chromadb？进阶
踩过坑：FastAPI 的同步接口跑在线程池里，如果 chromadb 是在工作线程里"首次导入+首次建客户端"，它的 Rust 绑定会初始化失败报错、首次请求 500。我在服务入口顶层（主线程）先 import chromadb，让它在主线程完成首次导入，问题就没了。
这是很"真"的工程细节——体现你真跑过、真 debug 过。面试官会眼前一亮。

七、评测（软肋区 · 必须补）

⚠️ 这层是你目前最容易被问倒的地方。哪怕没做完，也要能讲清"该怎么评"。
Q31你怎么证明你这套 RAG 答得准？必背
分两层评：① 检索质量——Recall@k（该被召回的有多少被召回）、MRR、NDCG；② 生成质量——忠实度（Faithfulness，答案是否只依据检索内容）、答案相关性。做法是构造一批"问题 + 标准答案/标注相关片段"的测试集，跑指标量化。
"我觉得它答得挺好"是零分答案。面试官要的是可量化、可复现的评测意识（这也是 RAGAS 这类框架在做的事）。
Q32Recall@k、MRR、NDCG 分别是什么？进阶
Recall@k：前 k 条里命中了多少比例的相关片段（召回全不全）。
MRR（Mean Reciprocal Rank）：第一个正确结果排名的倒数的平均（越靠前越高）。
NDCG（Normalized Discounted Cumulative Gain）：考虑"相关程度分级 + 位置折损"的排序质量指标。
面试官常让你"举个例子"。记住 NDCG 的关键：位置越靠后、折损越大；顺序错了分数就掉。
Q33你现在做过 eval 吗？
诚实说：目前是"人工抽查 + 少量固定问题"的功能验证，还没上系统的指标评测——这是我知道的短板，下一步就打算引入 RAGAS 或自建评测集，把 Recall/NDCG/忠实度跑起来。
不会的地方坦率承认 + 给出补课计划，比硬编强。"我知道该怎么做但还没做"是加分项。

八、局限与演进

考你对自己项目的"下一步"有没有想清楚。
Q34你现在知识库才 1 个文档、6 个片段，这算项目吗？
目前是最小可运行版本（MVP）——先跑通"服务化 Agent RAG"的骨架，语料是我自用的偏振测量资料。骨架是通用的：换更大的真实语料（论文/实验记录/设备手册）就能直接扩展，不用改架构。
把"小"讲成"刻意的 MVP 策略"，并强调架构可扩展。
Q35要提升检索质量，你会怎么做？进阶
按性价比排序：① 混合检索（BM25 关键词 + 向量，用 RRF 融合）——解决专有名词召回；② 重排（Rerank）——先粗召回多、再用 cross-encoder 精排取前几；③ 查询改写（query rewrite / HyDE）；④ 调 chunk 与 k（用评测数据定）。
能说出 RRF、Rerank、HyDE 这些词，说明你读过生产级方案，不只是入门。
Q36你这个项目的下一步规划？
三步：① 语料换成真实光学资料、补齐评测；② 加工具调用层——让 LLM 能调用 Python 脚本处理偏振数据（画电压-延迟曲线、算 Stokes 参数）；③ 用 LangGraph 搭状态机（检索→判断够不够→跑计算→出报告）+ Docker 部署。
这正好对应学习清单的二、三梯队和"杀手锏项目"，讲出来显得路线清晰。

九、杀手锏问题（高能区）

这类题没有标准答案，考的是"边界意识"和"诚实"。答好直接拉满印象分。
K1用户问的内容知识库里根本没有，你怎么防止它瞎编？
靠三重约束：① system_prompt 明确"只能基于检索内容，没有就说『知识库中未找到相关答案』，禁止编造"；② 检索没命中相关片段时，让模型如实说不知道；③ 可加相似度阈值——低于阈值就不喂给模型。但坦白讲，约束是概率性的，不能 100% 保证不幻觉。
最后那句"不能 100% 保证"是加分项——面试官反感"打包票"的人。
K2你这套和"把资料直接贴进 prompt"有什么本质区别？
贴进 prompt 是把全部资料硬塞——受上下文长度限制、贵、且资料一多就装不下、还淹没有效信息。RAG 是"按需检索"：只在回答某问题时动态取最相关的几块，可扩展到海量文档、token 成本可控、且能溯源到出处。
区别在"全量硬灌 vs 按需精准取"，以及可扩展性。
K3你说你"构建了 RAG 系统"——到底哪部分是你写的？
框架（LangChain/LangGraph/FastAPI/Chroma）是现成的，我负责的是"组装 + 决策 + 排障"：知识库切分策略、检索工具的描述设计、system_prompt 的约束、会话隔离方案、服务化与异常处理（429/超时/启动优化/线程坑）。用不用框架不是关键，能不能说清每个选择的理由才是。
别硬吹"我造了轮子"。诚实区分"框架能力"与"我的工程决策"，反而更可信。
K4如果让你把这个项目从 0 再讲一遍架构，你会怎么画？
四层：①数据层——文档 → 切块 → 本地 BGE 嵌入 → Chroma 落盘；②检索层——把 retriever 包成工具（Agent 自决调用）；③生成层——create_agent（LLM + 工具 + 会话记忆）+ 云端大模型；④服务层——FastAPI 暴露 HTTP 接口 + 异常映射。
能一口气画出"数据 / 检索 / 生成 / 服务"四层，说明你脑子里有系统全貌——这是"系统感"，正是 Agent 岗最看重的。

十、简历话术（直接可用）

一句话项目描述：基于 LangChain Agent + FastAPI + Chroma，构建光学领域 RAG 智能问答服务，实现「模型自决检索 + 多轮会话 + HTTP 服务化」。

三个技术亮点：
1. Agentic RAG：用 create_agent 把检索封装为工具，由 LLM 自主决定是否检索，避免无效检索与无关上下文污染；
2. 本地化向量检索：BAAI/bge 中文嵌入 + Chroma 持久化，无 API Key、重启不丢；
3. 服务工程化：FastAPI 服务化 + 会话隔离（thread_id）+ 429/超时异常处理 + 启动惰性加载优化（12s→0.6s）。
